# 工程

## webpack配置详解

### 入口（Entry）

指定打包的入口文件，告诉Webpack从哪个文件开始，构建内部的依赖图。通常是一个js文件，也可以是一个对象，包含多个入口文件

### 出口

指定打包的出口文件，告诉Webpack将打包后的文件放在哪里以及如何命名。

path：输出目录的绝对路径，必须使用path.resolve()生成。

filename：主入口文件的名称，可以使用[name]、[contenthash]等占位符。

chunkFilename：非入口（如动态导入）代码块的名称。

publicPath：为所有资源指定一个基础的URL路径，通常用于CDN部署

```js
const path = require('path');

module.exports = {
  output: {
    path: path.resolve(__dirname, 'dist'),        // 输出到项目根目录下的 dist 文件夹
    filename: '[name].[contenthash].bundle.js',   // 入口文件
    chunkFilename: '[name].[chunkhash].chunk.js', // 非入口文件
    publicPath: '/',                             // 静态资源引用路径
  }
};
```

### 模式

development：启用NamedChunksPlugin和NamedModulesPlugin，打包速度更快，代码不压缩，方便调试。

production：启用FlagDependencyUsagePlugin、TerserWebpackPlugin等，自动进行代码压缩、Tree Shaking等优化。

none：不使用任何默认优化。

### 模块

module是Webpack处理不同类型文件的核心。通过配置rules，可以为不同类型的文件指定不同的Loader

test：一个正则表达式，匹配需要被处理的文件类型。

use：指定使用的Loader，执行顺序从后往前。

include/exclude：明确Loader的作用范围，能有效提升构建速度。

### 插件

Loader用于转换特定类型的模块，而Plugin则用于执行范围更广的任务，如打包优化、资源管理和环境变量注入

HtmlWebpackPlugin：自动生成HTML文件，并自动注入打包后的JS/CSS资源。

HotModuleReplacementPlugin：启用模块热替换（HMR）。

DefinePlugin：允许在编译时创建全局常量，用于区分开发/生产环境。

loader和plugin执行时机

| 角色 | 执行时机 | 本质 | 核心能力 |
| loader | 在编译阶段（make流程中）处理单个模块文件时执行 | 文件转换器（转换函数） | 将非js文件（css/图片、ts）转换为webpack可识别的js模块 |
| plugin | 贯穿整个生命周期（初始、编译、输出、优化等阶段） | 功能增强剂 | 代码压缩（TerserPlugin）、提取 CSS（MiniCssExtractPlugin）、生成 HTML（HtmlWebpackPlugin）。 |

### 解析

extensions：自动解析的扩展名列表，引入模块时可以省略后缀。

alias：创建路径别名，简化导入路径。

### 其他重要配置

devtool：控制是否以及如何生成Source Map，用于开发调试。

'eval-cheap-module-source-map'：开发环境推荐，构建速度快。

'source-map'：生产环境推荐，能生成完整的独立.map文件。

devServer：配置开发服务器，提供热更新（HMR）、代理等功能

optimization：用于精细化控制打包优化，如代码分割（splitChunks）、压缩（minimize）等

externals：声明外部依赖，防止将某些库打包进bundle，通常用于通过CDN引入的库

cache：配置缓存策略以提升二次构建速度

performance：控制文件体积性能提示

## webpack构建流程

本质是一个静态模块打包工具，构建时完整打包

核心三大阶段（主线流程）

阶段一：初始化

合并配置和创建compiler

合并配置（webpack.config.js和命令行（cli）参数）

创建compiler对象，遍历所有插件，依次调用apply方法，传入compiler对象

阶段二：编译

从入口文件出发，递归构建依赖图

确定入口（Entry）：从配置的入口模块开始

创建compilation对象：它代表这次构建的上下文，包含本次构建的所有资源、依赖和状态

构建模块：

  加载（loader转换），loader的执行顺序是从右向左、从下往上执行

  解析：将转换后的代码通过acorn(js解析器)解析成AST（抽象语法树）

  依赖收集：遍历ast,识别require/import语句，将依赖的模块路径加入待处理队列

  递归处理：依次处理待处理队列中的模块，重复加载-转换-解析直到所有依赖都被处理完

生成chunk: 所有模块处理完后，根据entry和splitchunks配置，将模块组合成一个或多个chunk（代码块）

阶段三：输出

生成文件：compilation对象将chunk转换为浏览器可识别的内容（即bundle）

写入磁盘：调用compiler的emit钩子，将文件内容写入配置的output.path目录（如dist文件）

compiler和compilation的区别

compiler全局唯一，贯穿整个构建生命周期

compilation对象在每次重新构建时创建，它包含当前这次构建的模块、依赖和资源等细节

Tree Shaking (摇树优化)

本质是借助ES6的模块系统，只打包使用到的模块，避免打包未使用的模块，从而减小打包体积。

sideEffects的坑

```json
{
  "sideEffects": [
    "*.css",      // 保留所有 CSS 文件（因为 CSS 导入就是为了执行，不能删）
    "*.scss",
    "src/polyfill.js" // 保留 polyfill 文件
  ]
}
```

不配置可能会导致样式丢失或 Polyfill 失效，因为未使用的模块会被打包到最终的 bundle 中，导致样式无法正常加载。

Babel的干扰

如果Babel配置将ES Module转换为CommonJS模块，Tree Shaking 无法生效，必须强制Babel 保留 ES Module 语法给 Webpack 处理：

```json
{
  // babel.config.js
  "presets": [
    ["@babel/preset-env",{
        "modules": false // 关键！告诉 Babel 不要转换 import/export
    }]
  ]
}
```

splitChunks (代码分割)：缓存与加载的制胜法宝

核心配置思维导图

chunks：决定对哪些模块进行分割。

  'async'（默认）：只分割异步导入的模块（import()）。

  'initial'：只分割同步导入的模块。

  'all'（推荐）：无论同步异步，全部进行分割（最强模式）。

minSize：生成 chunk 的最小体积（默认 20000 bytes / 20kb）。小于这个大小的模块将不会被单独分割，避免 HTTP 请求过多。

minChunks：模块被引用多少次才被分割（默认 1）。常用于抽离公共业务组件（如设置 minChunks: 2，即至少被 2 个地方引用才抽离）。

cacheGroups（缓存组）：这是配置的灵魂，用于将符合条件的模块分到同一个组里打包

```js
// webpack.config.js
optimization: {
  splitChunks: {
    chunks: 'all', // 一网打尽
    minSize: 20000, // 20kb 以下不分割，减少请求数量
    minChunks: 1,
    cacheGroups: {
        // 1. 第三方库（vendor）抽离
        vendor: {
            test: /[\\/]node_modules[\\/]/,
            name: 'vendors', // 固定文件名，利用浏览器强缓存
            priority: 10, // 优先级最高，优先匹配这个规则
            reuseExistingChunk: true // 如果当前块已被复用，则直接引用，不重复生成
        },
        // 2. 公共业务组件抽离（如 utils、components 里的公共代码）
        common: {
            minChunks: 2, // 至少被 2 个入口引用
            name: 'common',
            priority: 5,
            reuseExistingChunk: true
        },
       // 1. 【核心】Vue 全家桶独立打包
        vueFamily: {
            name: 'chunk-vue-family', // 生成的文件名，如 chunk-vue-family.[hash].js
            test: /[\\/]node_modules[\\/](vue|vue-router|pinia|vuex|axios)[\\/]/,
            priority: 20, // 优先级必须高于下面的 vendors (通常是 -10)
            chunks: 'all',
            reuseExistingChunk: true,
            enforce: true, // 忽略 minSize 等限制，强制生成
        }
    }
  }
}
```

致命陷阱：maxInitialRequests（初始请求数）

默认情况下 maxInitialRequests 为 25，如果分割的chunk太多，超过限制，webpack会主动合并部分小chunk，导致你的分割配置看起来不生效

项目优化打包体积

第一步（Tree Shaking）：先检查 sideEffects 配置，确保 node_modules 中的无用代码被剔除，并且 Babel 必须设置 modules: false。这能将 lodash 这种大库从 500kb 压到只留你用到的 10kb 函数。

第二步（SplitChunks）：将剩下必须保留的代码分层。

react/vue 等基础框架放在 vendors（变动极少，走强缓存）。

业务公共组件放在 common（避免每个页面重复打包）。

路由页面用 import() 动态导入（配合 chunks: 'async'），实现按需加载。

vite怎么处理这两件事情

Tree Shaking：Vite 的生产打包底层使用 Rollup，Rollup 原生天生支持 Tree Shaking，你只需在 vite.config.js 中配置 build.rollupOptions.output.manualChunks 即可。

SplitChunks：Vite 没有 Webpack 这么复杂的 splitChunks 配置，它推荐使用 manualChunks 进行手动分割。

```js
// vite.config.js
export default {
  build: {
    rollupOptions: {
      output: {
        manualChunks: {
            'vue-vendor': ['vue', 'vue-router', 'pinia'],
            'element-plus': ['element-plus'],
            'utils': ['lodash-es', 'dayjs']
        }
      }
    }
  }
}
```

验证打包效果

webpack使用npm run build -- --report，会自动生成一个 dist/report.html，打开浏览器即可看到各 chunk 的体积占比。

vite安装 rollup-plugin-visualizer 插件，配置后在 build 时生成 stats.html 可视化视图。

```js
// vite.config.js
import { visualizer } from 'rollup-plugin-visualizer';
export default defineConfig({
  plugins: [vue(), visualizer({ open: true })],
});
```

## vite打包细节

vite开发环境使用esbuild按需编译，生产环境基于rollup进行打包

esbuild 编译速度更快，支持 ES Module 语法，不支持 CommonJS 模块。rollup 编译速度慢，支持 CommonJS 模块，不支持 ES Module 语法。vite 生产环境使用 rollup 打包，因为 rollup 支持 Tree Shaking，而 esbuild 不支持 Tree Shaking。

vite构建的核心是用rollup引擎 跑vite插件生态

构建流程

阶段一：预构建

Vite 会使用 esbuild 扫描你的 node_modules，将那些 CommonJS 格式（require）或包含大量内部文件的库（如 lodash-es），提前打包（预构建）成单个 ESM 格式的模块。

阶段二：入口解析与依赖图谱构建

入口发现：以项目根目录的index.html为入口，解析 HTML 中的 `<script type="module" src="/src/main.js">`，确定真正的 JS 入口。

路径解析：处理 @ 别名、node_modules 路径，以及 Vue 单文件组件（.vue）的解析

模块图构建：Rollup 从 main.js 开始，递归遍历所有 import 语句，构建出完整的静态依赖图谱（这是 Tree Shaking 的基础，必须是静态 ESM 才能分析）。

阶段三：转换与加载

遍历模块：Rollup 按依赖图顺序读取每个文件

插件链处理：文件内容会经过 Vite 插件链的 transform 钩子。

.vue 文件：@vitejs/plugin-vue 将其拆解为 template（编译为 render 函数）、script（TS 转 JS）、style（提取为 CSS）。

TS/JSX：Vite 默认使用 esbuild 进行语法转译（这里没有用 Babel，所以极快）。

CSS/静态资源：转换为 JS 导入或单独提取。

阶段四：代码优化与分割

Tree Shaking（摇树）：Rollup 利用阶段二的静态依赖图，标记出所有未被使用的 export（死代码），并在后续步骤中剔除。此时 package.json 中的 sideEffects 配置起到关键作用。

Chunk 分割（代码分割）：Rollup 执行 output.manualChunks 逻辑（你的配置）。

如果你写死了 manualChunks: { vendor: ['lodash-es'] }，所有 lodash 代码会强制合并进这个文件，从而解决“两个块都有 lodash”的重复问题。

如果是动态函数，则按规则分配文件名。

公共代码抽离：将多个入口共用的模块抽离成单独的 Chunk（Vite 默认的 vendor 分裂策略比 Webpack 保守一些，所以需要你手动干预）。

阶段五：压缩与输出

代码压缩（Minify）：

Vite 默认使用 esbuild 进行压缩（极快），替代了传统的 Terser。

如果追求极致压缩率，可以在 build.minify: 'terser' 切换回 Terser（但会慢很多）

资源哈希（Hashing）：为文件名注入 [contenthash]，利用浏览器缓存。

Manifest 生成（可选）：如果你配置了 build.manifest: true，Vite 会生成 manifest.json，用于后端或 SSR 映射资源路径。

写入磁盘：Rollup 将所有的 Chunk、CSS、HTML（处理过静态资源路径的）写入 dist 目录。此阶段触发 visualizer 插件，生成你看到的矩形树图。

## webpack和vite有哪些区别

| 维度 | webpack | vite |
| 启动方式 | Bundle打包，必须全量构建完整依赖图，才能启动dev server | no-bundle 通过浏览器原生ESM,按需编译，启动极快 |
| 更新方式 | 全量更新，即使只修改一个文件，也会重新打包大量相关模块 | 按需更新，只编译修改的文件并替换，其余模块走浏览器缓存 |
| 生产打包 | 成熟稳定，优化策略极其丰富（tree-shaking、splitChunks 等） | 底层依赖 Rollup 进行生产打包，亦非常优秀，但生态插件丰富度略逊于 Webpack |
| 处理逻辑 | JS 主导：所有资源通过 JS 逻辑进行转换和加载 | ESM 主导：利用浏览器原生解析能力，dev 和 build 用两套工具（esbuild + rollup）|

## CommonJS vs ESM(ES Module)

Tree Shaking（摇树优化）的核心原理是：在打包时，通过静态分析代码，把那些被定义了但从未被使用过的代码（Dead Code）安全地移除掉，从而减小最终打包体积。

在这个领域，ESM（ES Module）天生支持 Tree Shaking，而 CommonJS（CJS）极难甚至无法进行有效的 Tree Shaking。

特性 | ESM (ES Modules) | CommonJS (CJS)
加载时机 | 编译时（静态解析）| 运行时（动态执行）
依赖关系 | 静态结构，可画依赖图 | 动态执行，难以预测
Tree Shaking | ✅ 完美支持 | ❌ 极难支持（除非借助插件强转 ESM）
导出机制 | 引用绑定（Live Bindings）| 对象属性拷贝
代码位置 | 必须在顶层 | 可以在任何位置

## 代码懒加载

1.路由懒加载

在 Vue Router 或 React Router 中，利用动态 import() 语法，实现页面级别的按需加载。

底层原理：打包工具（Rollup / Webpack）遇到 import() 语法时，会自动进行代码分割（Code Splitting），把对应的模块单独打包成一个独立的文件。

2.组件懒加载

如果某些重型组件（如图表组件、弹窗、编辑器）不是一进来就展示的，可以把它定义为异步组件。

```js
import { defineAsyncComponent } from 'vue'

// 只有渲染这个组件时，才会去下载对应的代码
const HeavyChart = defineAsyncComponent(() => import('@/components/HeavyChart.vue'))
```

3.第三方库懒加载（如按需引入）

像 echarts、xlsx 这种体积巨大的库，如果不是每个页面都用，可以在用到它的函数内部调用。

```js
async function exportExcel() {
  // 只有点击导出按钮时，才去下载 xlsx 库
  const XLSX = await import('xlsx');
  XLSX.writeFile(...);
}
```
